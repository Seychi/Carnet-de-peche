## 🔴 Finding principal (à lire en premier) : le correctif est en prod, mais le Service Worker servait l'ANCIENNE page

Au premier chargement, `/notifications` affichait encore **l'ancienne copie** (maître « Alertes « fenêtre optimale » … Réservé aux abonnés Local et Itinérant », et le récap hebdo intitulé « Un pêcheur a interagi avec toi »). Ce n'est PAS un correctif manquant :

- **Vercel** : le déploiement de production courant est bien `aa4a28d` (`dpl_EbKQJPh3NvFdTSb8PGBkJa5ddWuG`, state READY, target production).
- **Le commit `aa4a28d` contient les fixes** (vérifié `git show HEAD:…`) : `PushSettingsToggle.tsx` rend « Notifications push » ; `describe()` a bien les cas `weekly_digest` / `big_tide` / `species_closure` / `followed_catch` / `nearby_outing`.
- **L'origine sert le bon code** : un `fetch('/notifications', {cache:'no-store'})` renvoie le NOUVEAU contenu (« Notifications push » ✓, plus d'ancienne copie ✓, « Ta semaine de pêche en résumé » ✓), `x-vercel-cache: MISS`.
- **Le coupable = le Service Worker PWA** (`/sw.js`, caches `cdp-v2-shell` / `cdp-v2-pages` / `cdp-v2-assets`). Il servait la version cachée de la page. **Après `caches.delete(...)` + reload, la page affiche le bon build sprint-51.**

**Pourquoi c'est important :** tout utilisateur PWA déjà venu (= cache SW existant) peut continuer à voir les pages **d'avant sprint-51** après le déploiement, jusqu'à rafraîchissement du cache SW.

**Mécanisme probable :** le `sw.js` du repo est en *network-first* pour les navigations (ce qui éviterait le problème une fois actif), MAIS la mise à jour du worker est conditionnée à un toast manuel « Mettre à jour » (pas de `skipWaiting` auto) et **`CACHE_VERSION` est resté `cdp-v2`** → le nouveau worker ne prend pas la main et l'`activate()` ne purge pas les anciens caches de pages (le filtre garde les caches de même version).

**Reco :**
1. **Bumper `CACHE_VERSION` → `cdp-v3`** à chaque déploiement qui change une page cachée : l'`activate()` purge alors les caches `cdp-v2-*` au prochain chargement.
2. Idéalement, **ne pas mettre en cache les routes authentifiées dynamiques** comme `/notifications` dans `PAGES_CACHE` (les ajouter à `isBypassed`, comme `/api/`, `/auth/`).
3. Vérifier que le toast « Mettre à jour » se déclenche réellement côté client.

> J'ai vidé le cache SW de TON navigateur pendant la QA : ta session affiche désormais le bon build. Les autres clients PWA restent concernés tant que le SW ne se met pas à jour.

## Limites de cette QA (à connaître)

1. **Mobile 390 px non capturé en pixel-réel.** Dans cette session, la fenêtre du navigateur **n'a pas pu être réduite** sous 1920 px (le `resize` est ramené à 1920 par l'environnement hôte), et l'astuce d'iframe 390 px **same-origin a été bloquée par `X-Frame-Options`**. Le DOM de `/notifications` est **identique** sur tous les viewports (server component `force-dynamic`) ; la mise en page responsive utilise des lignes flex `justify-between` + contrôles/pastilles `shrink-0` (pas de débordement attendu). **À spot-checker sur un vrai téléphone ou en mode appareil DevTools** (maintenant que ton cache SW est vidé, tu verras le bon build).
2. **Verrou « Fenêtre optimale » gratuit non testé en live.** Ton compte est payant et je ne peux pas créer de compte / saisir de mot de passe. La logique est correcte dans le code ; pour valider en live, ouvre toi-même une session sur un compte gratuit et je referai la passe sur la ligne verrouillée.
