## 3. 🔴 Critique — à corriger en priorité

### 3.1 Fuite des coordonnées GPS précises via `get_spots_for_scoring()`

**Constat (vérifié sur la base de prod).** La fonction `public.get_spots_for_scoring()` est `SECURITY DEFINER`, renvoie `id, lng, lat` **exacts** (`ST_X/ST_Y(s.geom)`) de **tous** les spots `visibility='public'`, **sans aucun filtre de visiteur**, et `EXECUTE` est accordé à `anon` **et** `authenticated` :

```
acl: postgres=X | anon=X | authenticated=X | service_role=X
has_function_privilege('anon', ...) = true
```

La clé `anon` (`NEXT_PUBLIC_SUPABASE_ANON_KEY`) est, par design, publique et présente dans le bundle navigateur. **Donc n'importe qui** peut faire :

```
POST https://glgciwwnpmgifyhbvxsw.supabase.co/rest/v1/rpc/get_spots_for_scoring
apikey: <anon key publique>
```

…et obtenir les **GPS précis de tous les spots publics**. Cela contourne intégralement :
- le **floutage 1 km** (`geom_public` / `spots_for_viewer`) — ta promesse anti spot-burning affichée sur la home (« Toute prise publique est floutée à 1 km, systématiquement ») ;
- le **gating payant** (coords précises = réservées Local/Itinérant).

**Portée aujourd'hui** : limitée (10 spots). **Mais** le plan sprint 10 vise **100-120 spots curés** → la fenêtre se referme avant que ça grossisse. À noter : un sous-agent d'audit avait d'abord cru, en lisant le fichier de migration, que la fonction était `REVOKE … FROM public` — la base réelle dit le contraire. D'où l'importance de la vérif live.

**Correctif** (nouvelle migration `025`, à appliquer après ta validation — je n'ai rien touché en base) :

```sql
-- 025_lock_get_spots_for_scoring.sql
revoke execute on function public.get_spots_for_scoring() from anon, authenticated, public;
grant  execute on function public.get_spots_for_scoring() to service_role;
```

Le cron de scoring (`compute-spot-scores`) appelle cette fonction via le **client service-role** (`lib/supabase/admin.ts`) → il conserve l'accès, rien ne casse. À vérifier après application : le cron quotidien produit toujours `spot_scores`.

## 4. 🟠 Majeur

### 4.1 Builds Vercel **Preview** cassés (env vars manquantes)
6 déploiements de branche `sprint-11` sont en **`ERROR`** (PR #1). Cause racine confirmée : `lib/env.ts` (l.20-21) exige `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_ANON_KEY` **dans tous les environnements** (pas gardées par `isProd`) → le module `throw` au build si elles manquent. Elles ne sont pas dans l'env **Preview** de Vercel.
- **Prod non affectée** (vars présentes). **CI E2E non affectée** (elle auto-provisionne depuis la stack Supabase locale).
- **Impact réel** : impossible de prévisualiser une PR/branche sur Vercel, et `next build` local échoue sans `.env.local`.
- **Fix** (dashboard Vercel → Settings → Environment Variables → cocher **Preview**) : ajouter les 2 `NEXT_PUBLIC_SUPABASE_*`. Hors outils Claude.

### 4.2 Lint désactivé partout
`next.config.ts` : `eslint: { ignoreDuringBuilds: true }` **et** CI `check.yml` : `pnpm lint` en `continue-on-error: true`. Rien ne bloque sur le lint, nulle part. Masque la dette connue (~360 `react/no-unescaped-entities`) **et** un vrai bug `eslint-config-next` v16 / flat-config. Le typecheck `tsc --noEmit`, lui, **est** bloquant (🟢 filet réel), mais le lint ne couvre plus les `core-web-vitals`.

### 4.3 4 vues `SECURITY DEFINER` signalées ERROR par le linter Supabase
`catches_for_viewer`, `spots_for_viewer`, `feed_posts_for_viewer`, `profile_stats`. Le linter alerte car une vue `SECURITY DEFINER` applique les droits du créateur, pas du visiteur. **Ici c'est en partie voulu** (ces vues SONT la couche de floutage). Vérifié : **aucune ne sélectionne de `geom` brut** → pas de fuite par ces vues. Recommandation : évaluer `security_invoker = on` (Postgres 15+) + RLS sur les vues, ou documenter explicitement le choix. À traiter **après** le 3.1.

### 4.4 Version de Node désalignée
Vercel build en **Node 24.x**, alors que `.nvmrc` + CI = **Node 20**. Risque de parité build/runtime (un comportement qui passe en local/CI mais diffère en prod, ou l'inverse). Aligner : fixer le projet Vercel sur Node 20, ou monter `.nvmrc`/CI sur un seul LTS.

- Multiple permissive policies (`catches` SELECT ×3, `feed_posts`/`feed_comments` DELETE ×2), FK non indexées (`feed_likes.user_id`, `reports.*`, `feed_posts.moderated_by`, `spots.created_by`), index inutilisés : sans impact à 10-14 lignes, à revoir quand le trafic monte.
